# ksf-runtime

## 职责

由当前宿主 Agent 执行：接住用户目标，保持有效授权，组织合适的能力，记住当前安排，持续推进并核对最终交付。

## 接住并推进目标

收到新消息，先判断是在继续、补充、纠正、临时插问、换任务、暂停还是取消。保留仍有效的目标、决定、成果和授权；无法判断且会影响下一步时，再澄清。

方法、事实和工具足够的一次性请求直接完成，遵守用户明确的能力和项目要求。临时插问保留主工作，答完不清空主任务。

其余没有有效安排、原安排不再适用或交付发生实质变化时，重新确定安排：

- 需要确定项目、切换项目或补项目/工程事实，使用引用的 project-route。
- 需要新选或改用能力，使用引用的 ability-route。

使用前，按本对象元数据的精确引用和实际来源，用下文 `context current --extras` 完整取得所需路由及其标记展开内容；已完整读过且仍在上下文、有效的原文直接复用。两者都需要时可一次装入，先补项目事实，再选能力。

把当前目标、必要事实、原安排和有效授权带过去，取得结果后接着推进。

路由返回预设失效、替代安排或影响执行的缺口时，采用前向用户说明。遵守明确的硬性要求，已有有效授权不重复询问。

下一步条件具备且已获授权，就实际执行。缺口只挡住依赖它的步骤，能独立继续的部分继续做。用户问状态时，回应后继续仍然有效的工作。

## 保存当前工作安排

工作需要跨轮推进，或已确定持续使用的能力时，保存当前工作绑定。当前只保留一项主工作，临时插问不替换它。

绑定记下目标、主归属、承接者、持续方法、必要文件和任务记录入口：

- `executor` 是当前执行职责；通用 Agent 直接处理时可以为 null。
- `methods` 是当前需要持续使用的方法。
- `files` 和 `taskRef` 指向必要资料及当前任务记录。

需要可靠接续的非项目工作，优先复用已有草稿和已授权记录。将本实例内需要重读的原件加入 `files`，已有任务记录时可用 `taskRef`；外部原件保留原处及实际入口。

确需保存时，由所用专业能力按授权办理，不自动建项目。恢复时补读工作原件；缺少可靠入口就说明缺口，不能把恢复能力正文当作已恢复工作进展。

能力使用精确版本和实际来源 `{ref,source}`，不从 cwd、同名对象或参与历史猜配。候选、审查对象和一次性方法不自动写入绑定。

需要更新时，用 `context work --json` 取得完整当前值和 etag，再用 `context bind --from - --if-match <etag> --json` 保存完整新值。只改受影响的部分；没有变化就不重复写入。
首次绑定、退出，或工作项目、关联项目、承接者和持续方法有变化时，有宿主提供的原生轮次就给同一次 bind 加 `--turn <原生turnId>`，便于归档查阅工作安排。工作项目始终是当前实际推进的项目。没有可靠轮次仍可保存安排。临时插问不触发绑定或归属声明。

新安排确定后，同轮执行 `context current --json`，核对所需能力、方法和资料已进入当前集合。

首次绑定或字段不清时，查阅 [context CLI](../../../docs/cli/context.md) 的结构示例。

## 每轮取得需要的正文

先核对 KSF_WORK_CONTEXT_V1 中的安排是否仍符合用户意图。有 readRequired 要求时，用 `context current --json` 取得清单和正文，补齐后再执行依赖这些内容的步骤。

核对命令是否成功、结果是否完整、是否有错误，以及各项来源和状态。已经完整读过、仍在上下文且没有变化的正文直接复用；新内容和变化项读取完整主文。

取得的整批正文完整读完且没有错误后，才将该次 data.delivery 原样交给 `context accept --from - --json`。清单、输出已生成或文件已落盘，都不能代替实际读取；失败或截断的一批不确认。

临时支持用 `context current --extras '<JSON数组>' --json`，每项为精确 `{ref,source}`。它不改主绑定；下次不带该项，就退出临时用途。

某项退出，只结束它在当前工作中的职责或资料用途。保留已确认的事实、决定和成果，共同需要的依赖继续保留。

## 切换、暂停和恢复

- **换能力：** 替换受影响的执行职责和方法，保留其他有效安排。
- **换主项目：** 建议在目标项目新开对话；没有创建指令就不自动创建。留在原对话时，更新绑定并退出旧用途。历史文字仍然存在，旧安排不再作为当前执行依据。
- **暂停：** 停止对应推进，保留绑定并设为 paused。
- **明确恢复：** 核对原安排仍有效，将 paused 改为 active，保留其他有效项，再继续。
- **上下文压缩或恢复：** 按 Hook 的当前清单补读。缺少 Hook、正文丢失或连续性不清楚时，在允许写入的情况下用 `context current --reload --json` 重建当前集合；不重选任务、不重放历史操作、不补造原生轮次。

绑定损坏时保留原件并报告，不能用参与历史猜一个新绑定覆盖。缓存损坏可以重建；缓存声称已读但正文实际已丢失时，按清单补读原件，不能把空 bodies 当作已有正文。

用户禁止写入时，不执行 bind、accept、reset、--reload、hooks 安装或参与登记；只读取得所需原文，说明安排未保存、读取未持久确认。恢复写入后，只保存仍有效的安排。

例：同一项目从 A 改由 B 执行，仍需要的方法 M 保留；临时方法 X 用完退出。压缩后恢复当前 B、M 和任务资料，不把历史上用过的 A、X 全部装回来。

## 衔接专业工作

交接时，确保所需能力正文已经取得，并带上目标、已有成果、用户决定、有效授权、相关资料和返回要求。

收到结果后，依据对应能力的专业结论，核对产物、证据和未决项，判断是否满足本次用户要求。有差距就把具体问题交回相应能力复核、补齐或返工，满足要求后再交付。

项目进展需要保存或恢复时，使用项目管理及 project-control 的相关方法，将核实后的任务记录入口保留在 `taskRef`。本搭档负责确认交接和保存已经实际完成；工作绑定、缓存或对话归档不能代替项目记录。

## 个人设置、参与和对话记录

实际采用能力前，用 `user-data read --object <id> --json` 读取它自己的设置。本次明确指令优先，其次是保存值，再其次是能力默认值。缺失不创建默认记录，损坏不当作缺失；候选阅读不采用其私人设置。

跟踪开启且允许写入时，每个对象在本原生轮次首次实际使用前，执行 `chat use --object <完整ID> --turn <原生turnId> --json`，使用返回的计数和动态值，不手算。身份不清时用 `chat sync --json` 核实。

变量按实际需要命名，更新带 etag；只有明确重新开始时才 restart，不清理其他对象或旧任务数据。禁写时参与不登记，并说明这一点。

普通对话走默认采集。采集从已发生的项目绑定变更和能力参与读取事实。仅在明确指定单轮归属，或处理记录限制时，使用真实 turnId、新 eventId 调用只读 `task declare --from - --json` 并保留完整回执。

涉及记录限制时，原样带上 Hook 给出的输入范围。范围缺失或同轮收到新增输入时，先用 `task input --turn <原生turnId> --json` 核对。旧声明不覆盖后续输入。

- 澄清引用的限制或明确指定单轮归属：capture。
- 仅本轮不记录：exclude。
- 持续不记录：pause。
- 恢复记录：resume。

确需补报的轮次使用 report 声明一个主要 ownership，其他放 relatedTargets。实际采用的能力与被审查、修改的对象分开。待创建目标沿用返回的 targetId，不按同名合并。采集历史不产生新授权；声明失败不阻断独立工作。

## 交付和结束

交付前核对：目标与安排仍符合用户要求，持续使用的能力已进入绑定或明确属于禁写时的临时采用，所需正文确已读到，动作确已执行，产物和证据可读，必要保存已完成，剩余事项和恢复条件清楚。

路由选好、计划写好、单条命令成功，或一轮报告标为 completed，都不等于整项工作完成。

本次主工作真正完成或取消后，处理必要保存，再用 `context bind` 提交 JSON null 清空当前绑定。有宿主提供的原生轮次时，退出项目沿用上面的 `--turn`。项目阶段与结项按项目管理的专业结论处理，保留项目记录、原件和成果。
