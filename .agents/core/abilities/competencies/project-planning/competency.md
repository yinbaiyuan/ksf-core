# 项目规划

## 结果与输入

独立结果是可核对的项目安排：成功条件明确，阶段按成果划分，事项对目标有贡献，硬依赖没有循环，当前承诺符合容量，关键假设和未决显式表达。适用于新计划、现状混乱或目标/范围实质变化；已有安排有效且只需推进时采用推进控制，不重排整个项目。

必需输入为已确认项目、用户期望结果、操作边界、当前事实及可取得原文；可选输入为期限、预算、负责人、资源和约束。先读根卡与管理主件；程序字段见[接口说明](../../../docs/project-management.md)，再读影响安排的具体来源。不足以定义成功条件时提出有理由的候选；未知估算、日期与责任不猜填。草案允许先留空并标明影响，不能把候选当承诺。

## 方法

1. **界定结果。** 从“做某功能/研究某问题”追问实际使用者、成果及成功条件；将手段与结果区分。写明纳入/不纳入的范围和关键约束。已有项目以最新用户要求和实际产物校准，历史资料不自动成为新要求。
2. **盘点基线。** 对每项已有成果标明已看到的产物、验证阶段、来源和未决。旧检查点的完成状态只是来源记录；检查它是否仍贡献当前目标，是否真的完成，是否需要重新验收。无证据时保留待核实，不把所有旧任务批量迁为正式承诺。
3. **形成阶段成果。** 按能独立验收的结果划阶段，给每阶段定义产物和验收条件。阶段不是硬依赖，也不是只按日历切块。长期项目先定义当前阶段与下一阶段方向，不制造遥远阶段的精确排期。
4. **拆为可交接事项。** 每项写清产物、目标/阶段关联、下一行动和可核对验收。过大到无法判断进展则拆分；小到没有独立成果或验收价值则合并。研究事项的产物可以是有证据的判断或排除结果，不能要求探索工作预先保证结论。
5. **建硬依赖与覆盖。** 只有前项结果是后项开始/完成的必要输入时才设硬依赖；共享主题、阶段/父子关系不产生阻塞。查环、失效引用、目标无覆盖及无目标事项。每个关键目标至少有阶段/事项承接，每个当前承诺能解释目标贡献；合理独立工作说明理由，不强凑关联。
6. **形成有限承诺。** 区分候选、接下来与当前承诺。先检查依赖、阶段、阻塞和资源，再按目标贡献、期限、解阻价值和风险排序。容量不足时明确延后或挤出哪项；估算基于可说明的依据，未知则用短探索/验证行动缩小不确定性，不虚构数值评分。
7. **核对与保存。** 提供完整安排及重要取舍，按现有授权推进。范围变化同时更新受影响目标、阶段、验收、承诺、资源/期限及风险，不能只追加待办。用公共 check 检查确定性问题，依 read 回执保存同一主件；程序通过之后仍审查语义覆盖和可执行性。

## 输出与质量

输出为现行计划或明确标为草案的差异：目标/范围、当前阶段、成果与条件、事项和硬依赖、承诺与优先理由、风险/待决、来源和下一行动。简单任务可用少量条目，不强制完整方法名或长报告。稳定身份用于引用和恢复，标题变化不另建重复事项。

失败信号与修正：目标只有动作没有结果→补成功条件；事项多但关键目标无承接→重查覆盖；所有任务都为当前承诺→依容量减量；只有“继续推进”→补具体产物和第一行动；时间精确但依据未知→撤回伪精度并设验证行动；新需求只叠加不取舍→重评原承诺与验收。

模拟正例：采购项目先形成可比较报价与兼容证据，再决定购买，采购行动显式依赖选型判断。反例：把“买最好的设备”直接设为高优先任务且无预算/验收。边界例：用户只要临时排序建议，可在上下文给出判断，不创建管理主件。

## 支持与验证

公共支持为 `project management read/check/write`、项目原文与宿主文件工具，接口及错误处理见共同契约。不能读取来源时停止依赖该来源的承诺，继续可独立安排的部分。当前模型不提供自动资源排程或后台调度。

本版没有独立对象偏好或跨项目状态；采用/恢复按公共 user-data 约定读取，不写项目正文到设置。方法依据是已保存的需求与项目管理实践的工程化设计，效果仍待真实任务比较。验证至少覆盖新计划、无来源、研究不确定性、范围变更、目标覆盖、依赖循环和容量取舍；记录计划是否改变实际下一行动，不能只验目录完整。

## 建立、接入与工作区安排

用户明确要求创建、导入、整理或补全项目时，先核对已有当前项目及必要同名档案，不能因新名称重复创建。归属不明把具体候选交回 runtime 按项目路由核实；已有归属的接入与新增管理安排分别判断，不因复制材料自动建立完整计划。普通任务补一个事实不触发项目创建。

材料处理采用声明引用的项目接入与补全基本功，读取实际有效定义及所需支持，按原件、版本、分区入口与冲突方法形成差异。新项目根卡使用 project write 预览、实际写入与读回；已要求持续管理时再建立同一管理主件。仅接入请求交付可继续入口，用户同时要求业务工作才执行后续业务动作。

根卡创建与完整更新使用 [project CLI](../../../docs/cli/project.md) 的 `write --dry-run`、实际 write、read/check；目标是项目目录名，输入为 metadata/body 信封。省略部分保留，提供 body 会整体替换，提交前核对最新正文。局部正文和项目资料可用宿主文件工具，普通元数据可用 metadata write；管理主件使用共同契约的条件写入接口，不能以根卡更新替代。本项负责写前基线、条件写入、入口同步与读回；并发冲突重读比较，多文件部分成功逐项说明。

### 接入的落实与核对

项目接入方法形成补全安排后，核对来源、项目落点、拟修改差异和已有授权，再落实根卡、分区概览及材料复制。专业事实和版本判断由所采用方法持有，本项保留唯一落点、基线、写入、验证及回退职责。普通外部材料按已确认默认复制并保留原件；来源变化保留副本并报告差异，不覆盖、不自动另存新版。内部工具的只读计划和实际 apply 分开；部分结果逐项核对，不从退出码推定全部成功或失败。项目内已有材料原位整理，工程使用下述创建与关联方法。导入记录属于项目资料，不进入对象 user-data。

### 工程仓库创建与关联

按已确定的项目目标和实际工作区安排，使用 [repository CLI](../../../docs/cli/repository.md) 执行已授权维护。用户已要求实际工程交付且缺少合适工作区时，可按默认位置创建并初始化本地 Git，不为同一安排重复确认；只有根卡或讨论需求时不顺带建工程。

1. 新建前核对 `repositories/<工程名>/`、已有根卡与父仓库忽略规则；当前实例的根 `.gitignore` 应包含 `/repositories/`。预览 `repository create <工程名> --dry-run --json`，再实际 create；默认 main 分支，无初始提交或远程。重复 create 只接受已经有效的独立 Git 根，不接管已有普通资料目录。
2. 根卡已存在后，预览并执行 `repository link <工程路径> --project <项目目录名>`，再 `repository check --project <项目目录名> --json`。CLI 输入的相对路径基于 KSF 根；根卡内的关联以根卡为基准保存。关联只写可选 `repositories` 元数据，保留正文和其他字段，不创建第二份仓库注册表。
3. 已有工程只关联，不改其分支、历史、远程或工程规则。需要解除时使用 `repository unlink <工程路径> --project <项目目录名>`；失效路径也可解除，工程文件保持原位。旧资料不随机制上线自动搬迁。
4. 创建、关联与业务文件分别验收；关联失败时保留已创建工程，核实后重试 link，不重复创建或删除工程。create 失败若返回 recoveryPath，先检查实际目录与部分状态，不盲目重试。仓库锁和项目写锁的范围见 CLI 文档。

工程初始化不授权 Git 暂存、提交、推送或创建远程仓库。项目归档、删除项目目录或解除关联均不连带删除工程；工程备份由其自身 Git、远程或其他已授权方式承担，父 KSF 仓库不会备份被忽略的工程正文。
