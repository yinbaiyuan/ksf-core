# 项目推进控制

## 结果、输入与边界

将项目现行安排、最新产物和变化转为有依据的现状判断、可做集合、下一行动/解阻行动及受影响的承诺调整。适用于进展复核、执行返回、依赖延期、风险出现或新需求插入；目标体系失效时返回规划，验收结论交验收方法。只对实际变化处理，不要求每日无变化也输出报告。

先读[共同契约](../../../docs/project-management.md)、根卡、管理主件及本次变化对应原文。核对项目范围、授权、当前任务关系、事项稳定身份、来源新鲜度及外部操作身份；没有最新产物时保留未知，不能仅从旧日期推断失败或完成。

## 方法

1. **恢复事实而非复述状态。** 比较现行安排与实际产物，区分工作事项状态、执行宿主运行状态、验收条件结果。来源已变就重读；执行退出、模型说完成或工具回执仅代表对应层级的事实。失败或未知操作先按原 ID 对账，不盲目重发。
2. **计算可做集合。** 公共检查核对未结束/未暂停、已纳承诺、硬依赖完成、无阻塞、所属阶段开启、有下一行动和可用在制容量。结果只代表这些记录条件具备，Agent 再核对真实工具、权限、输入和资源是否可用。高优先且不具备条件时优先考虑解阻，而非强行启动。
3. **排序并解释取舍。** 在可做集合内比较目标贡献、解除后续阻塞的价值、期限、风险暴露和实际资源。优先级理由必须能指向当前事实；同级无需造精确分数。当前在制已满时先收口、解除阻塞或减少承诺，不把多开会话当作提高项目容量。
4. **处理阻塞与风险。** 记录已发生阻塞的事实、影响事项、解阻行动、责任与恢复触发；风险记录尚未发生的不利条件、影响、应对和复核条件。能独立做的验证/替代继续执行。只有全部关键路径受阻时才整体等待；不能因一项受阻把所有工作都标为停止。
5. **控制变更。** 新需求先判断是澄清、缺陷、范围增加还是原决定被推翻。比较收益、成本、不确定性和对原承诺/验收的影响，推荐插入、替换、延后或拒绝；已有授权范围内直接落实，超出范围的关键决定交用户。不隐式加入承诺，不悄悄修改原成功条件掩盖偏差。
6. **形成专业交接。** 交接稳定事项 ID、目标与产物、验收条件、输入和路径、依赖、允许修改范围、外部动作边界、返回要求和触发。只读取任务相关资料。需要真实执行时沿现有能力安排承接；管理机制不自行建立定时器、执行会话或发送消息。
7. **更新和反馈。** 收到实际成果后仅更新受影响事实和承诺，保留来源及未决。公共 check/write 使用同一版本条件；冲突时重读、比较、合并，不能丢弃别人修改。没有实质变化可不写入。交付当前判断、推荐下一行动、理由、变化和恢复条件，不以待办列表代替已授权推进。

## 质量、案例与验证

合格输出能回答“为什么现在做、依赖什么、占用什么容量、何时返回、依据什么更新”；高优先受阻事项应有解阻行动。不可做事项必须给实际理由，计划与事实不一致应显式校正。

模拟正例：上游资料延期，采购未启动；先验证另一项不依赖该资料的兼容条件，并将延期影响和重评时间交回项目层。反例：按优先级数组启动全部事项，忽略已满容量和阻塞。边界例：一次代码执行成功只转待验收；不能据此完成阶段。来源缺失或工具不可用只阻止依赖部分，不反复重新路由。

本版公共程序支持依赖、容量、版本和来源检查；不提供自动领取、租约、运行重试、全资源排程。无另存的对象偏好/跨项目状态，采用/恢复按公共 user-data 约定读取，业务事实留在项目主件。

验证覆盖依赖延期、取消前置、同时修改、插入紧急需求、容量已满、执行结果未知、暂停恢复及无变化复核。观察实际动作是否符合判断；程序测试、人工走查与独立会话效果分别记录。

## 项目恢复、暂停与检查点

项目管理主件持有现行目标、阶段、事项和承诺；检查点只保存具体执行的恢复细节，并用稳定事项 ID 关联，不能维护第二份项目计划。普通专业任务不因此强制经过全项目规划。

恢复顺序：先复核根卡身份/scope与明确任务，再读取管理主件（缺失不创建），确认关联事项及现行承诺；随后读取指定检查点、实际产物、必要工程规则与精确定义，校正来源版本和最新用户决定；再核对有效授权与原操作结果，最后执行第一项条件具备的动作。多项未决不能凭修改时间猜选，已完成/取消不自动重开。外部动作结果未知先按原 ID 对账，记录只是来源而非永久授权。

用户暂停或提前交接时停止相应执行，保留事实、产物、未决和恢复触发，必要时调整对应事项而非全项目一律暂停。归档调阅保持只读；明确复工请求由本项核对保留成果、过期事实、范围、依赖与承诺，形成恢复安排，物理恢复使用验收收口基本功持有的归档/恢复方法。原位 status=archived 的旧项目按明确请求更新根卡，不把 restore 无变化当作已激活。

### 检查点保存

用户要求保存、暂停或交接，或持续任务已授权维护项目记录且发生实质进展时，按[唯一检查点约定](../../../docs/runtime/task-checkpoints.md)保存恢复信息。普通问答不例行建文件，不为没有归属的任务自动建项目。项目恢复判断由本基本功持有，runtime 保持通用任务与授权连续；资产维护提供通用基线、写入和验证保障。

先读取原检查点和根卡，用宿主文件工具局部更新正文；用 metadata read/check 核对元数据，并重读正文与必要产物入口。先保存检查点，再补根卡链接；任一步失败只报告实际已完成部分，不把两文件写入称为事务。检查点不放入 runtime-data，也不复制工程正文、凭据、完整聊天或未经核实的外部执行结果。
