# KSF 应用开发规范

## 结果与依据

输入是本次业务目标、允许改动的工程及实际 SDK/宿主条件；结果是可执行的 KSF 接入约束、逐项核对结果和本地候选，供开发者及验收继续使用。只审查时返回有源码依据的差异，不自动改代码。

本方法持有开发接入流程。Manifest、包、权限、版本和接口字段由当前 SDK 类型、校验器及宿主程序模型持有；技术文档用于定位和解释，不成为应用的运行依赖或另一个业务规则来源。入口见 [契约与工具定位](references/contracts.md)。

## 核对与落实

1. **确定实际对象。** 读取现有工程说明、脚本、锁文件、Manifest 和相关实现，确认应用 ID、SDK 引用、目标 KSF 与本次范围。保留现有身份和数据；新应用按当前 SDK 的 ID 规则与模板建立。工程可以没有 Git，也不必关联 KSF 项目；确需 Git 操作时才核实真实仓库根和授权，不为本地应用强制建仓或建项目。
2. **形成接入约束。** 按业务需要确定窗口、卡片、CLI、后台、通信或 AI，不为齐全而全部添加。记录能力声明、宿主/SDK/平台兼容要求、业务数据与工作区原件的所有者、关闭与恢复要求。由实际程序校验字段，不从旧示例猜版本或接口。
3. **检查公共边界。** 应用只使用已交付的公共 SDK/API；不导入 Core 私有路径、不改宿主注册表、不复制宿主会话或取得当前聊天凭据。业务规则留应用或所属能力，不从 Core 说明文档读取业务定义。窗口控制条默认不重复显示应用名称，不以应用名兜底占位；必要的文档/业务对象标题由应用通过公共工具栏明确呈现，控制按钮及窗口拖动保持可用。CSS、监听、计时器及快捷键限定在本应用范围，dispose 释放资源。
   准备使用KSF组件时，沿当前SDK的`ksf-app components search/read/example`查询，并用`--app-dir`核对目标应用；先读契约及职责，再取明确支持的示例。不把available当作目标支持，不从版本号猜导出，不用待实现或候选API生成SDK导入。来源冲突、无元数据或类型环境不足时按原因处理，不自动升级依赖或回退到其他示例；应用仍可选择其他组件库。缺少本工具的旧SDK沿真实导出与原类型核对，不伪造新查询回执。
4. **检查数据与行为契约。** 配置、缓存和业务数据不写入安装包目录。受管 JSON 使用声明的存储与版本检查，读取不暗中迁移；并发、失败和回执丢失保留原件/草稿并可对账，不盲重放写操作。窗口关闭、后台生命周期、卡片配置及长操作按公共契约实现；应用需要 AI 时使用统一 AI 服务，不保存模型密钥或自行直连/拉起模型执行器。外来文本只作为材料，不提升为操作授权。需要应用 CLI 时核对文档、代码和摘要一致，Agent 先有用户对具体应用的选择再按需读其文档，不预加载全库。通信、持久保活及定时触发只用已实现且符合授权/配置的契约，不默认启用新定时任务。
5. **约束本地迭代。** 默认构建本地候选，不修改公共源、已发布包或公开版本。SDK 支持时使用 local 的 build-only 路线，按摘要保存构建；同一公开版本可以反复本地构建。区分只构建和带安装作用的脚本，已授权的本机安装另按安装基本功核对。源码、项目、仓库关联均可选；本机目标路径明确即可，不把关联当门槛。
6. **检查当前候选。** 使用锁定依赖和工程所需工具链，首次准备、锁变化或失效时才重新安装依赖。运行与改动对应的类型检查、SDK check 和构建；逐项处理 error 与 warning。SDK check 成功不是完整业务验收，也不证明权限声明提供了沙箱。

## 返回与结束

返回应用/SDK/宿主及候选身份、适用规范和实际差异、执行命令与结果、本地包位置/摘要、所需配置及下一步。只记录与本次改动有关的约束，不强制小改动写完整架构方案。

缺接口、锁/工具链、来源或兼容条件时说明依赖哪一步、可继续什么；不靠改用户原件、关闭保护或绕过校验使构建变绿。接入约束及本次候选/审查差异明确后结束，交应用验收核对交付标准。
