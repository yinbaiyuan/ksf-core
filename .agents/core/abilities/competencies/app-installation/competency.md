# KSF 应用安装与更新

## 输入与结果

输入为明确的目标 KSF、应用 ID、候选来源/包及本次安装、更新或恢复授权。输出安装前后身份、来源、版本/摘要、启用和 active/pending 状态、业务数据核对及恢复限制。普通本机操作不等于公开发布。

本方法持有安装流程；原生宿主负责兼容、完整性、来源锁、受管数据及安全切换。不能编辑安装索引或已安装文件替代原生安装，不能为测试成功修改用户业务数据。

## 依据来源选择路线

- **本地应用：** 直接导入 .ksfapp 即可，源码、项目和 Git 仓库均可选关联。用应用商店导入或当前公共 local 工具安装；SDK 本地构建按摘要更新，公开版本不必随每次本机修改递增。包与资源复制进实例后，源码/原包暂时不可访问不应成为运行条件。控制条不默认重复显示应用名，应用身份在菜单、Dock和无障碍窗口名称中正常保留；来源及关联放详情。
- **应用源安装：** 从原安装源获取并安装最新兼容候选，核对源身份、包摘要及实际宿主要求。应用源离线与本地运行能力分别核对；使用缓存/离线基线时标明最新版本尚未确认，不拿任意其他源的同名包覆盖。
- **更换来源：** 用户明确要将同 ID 源安装替换为本地时，以明确安装动作完成并保留数据/安装身份。当前 local 入口需要显式 replaceSource；没有进入/退出开发的运行模式，也不隐式恢复另一套正式基线。来源替换未获授权时先保留候选和具体差异，继续不依赖该动作的工作。

## 安装过程

1. 核实目标实例、现有安装记录、候选 Manifest/摘要和来源；明确代码更新、格式迁移及卸载的实际后果。新应用不能因为没有安装记录就被认定没有历史数据。
2. 现有安装先用宿主的数据检查能力核对声明存储及兼容；为日常实例更新保留必要的安装记录和业务数据基线/备份。临时验收只用虚构数据。数据损坏、要求迁移或来源冲突时保留现场，先在隔离实例核对修复/迁移路线，不写空数据、不卸载绕过门禁。
3. 核对包内容、能力声明与可信来源符合本次授权，再使用原生入口。当前 CLI 的只读入口为 `ksf app local status <appId> --json`、`ksf app data inspect <appId> --json`；local install/link 使用 `--from` 的 JSON 输入。参数以实际 `ksf app --help`、SDK 工具和返回校验为准，不编造未提供的 source install CLI。源安装可使用应用商店。
4. 通过应用关闭保护完成待保存内容，等待旧窗口及在途操作排空；保存失败先保留草稿。pending 表示尚待切换，不能当作新代码已运行，不 force 终止保存。正常应用安装不重启主服务；确实涉及宿主更新时另行取得对应授权，由系统维护承接并说明服务变化。
5. 读回实际 active/pending、来源、摘要、启用和安装身份，重新打开原应用核对必要业务内容；比较数据及其他应用是否出现本次范围外变化。结果未知先对账，不盲目重复安装或恢复旧快照。

## 停用、卸载与恢复

按用户实际要求使用原生入口，说明数据和配置的保留范围并读回核对。代码回退先检查旧包能否读取当前数据，不自动回退业务数据；旧数据恢复是另一项明确的数据恢复动作。卸载不作为更换来源或绕过兼容的默认手段。

## 结束

实际切换和数据核对完成才报告安装通过；仍 pending 或有数据/运行缺口时交对应状态及继续条件。记录可定位的包、数据基线、操作和回执，避免把机器路径或真实业务内容放入公共包。
