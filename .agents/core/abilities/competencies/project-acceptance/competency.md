# 项目验收与收口

## 结果与输入

独立结果为可追溯的验收结论：逐项条件、实际证据、通过/未通过/待核对、复核者与时间、遗留问题，以及继续、返工、延期、取消或完成的理由。适用于执行返回、主动验收和阶段/项目边界；不替代目标规划或把收口自动扩展为发布、部署、归档和知识沉淀。

先读当前约定条件、对应实际产物与验证记录，并核对最新用户要求。没有验收条件先按目标补可观察的候选，显式说明依据，不能事后降低标准制造完成。证据入口存在不证明内容正确，网页引用也不证明本地效果。

## 方法

1. **回到交付。** 将原请求及有效修正逐项映射到成果和验收条件，检查遗漏和范围漂移。确认待验收版本/环境与实际交付一致；旧版本测试不能证明新版本可用。
2. **分层取证。** 文件/结构检查、单元或专项测试、当前 Agent 实际使用、独立会话、真实设备/用户验收分别记录。按条件选择足以支持结论的证据；没有要求的平台不强做，也不把未执行范围列为已通过。
3. **逐项判断。** 读取实际产物和测试结果，说明支持哪个条件、条件是否满足、证据局限。passed 需要可访问证据、实际复核者与时间；failed 说明差距与返工行动；pending 保留缺失、责任和恢复条件。运行结束、Agent 自述、截图存在都不能自动转 passed。
4. **检查依赖与遗留。** 事项完成前检查硬依赖已完成、承诺成果和验收全部通过。阶段完成还要检查本阶段事项已完成或有理由取消，阶段成果按自己的条件验收；事项全完成也不自动完成阶段。取消事项不是通过验收，应记录取消原因/影响，重评依赖它的工作。
5. **形成收口决定。** 达标则完成对应层级；有缺口则保留待验收/返工或延期，写明确下一行动；业务目标失效可建议取消但不伪装成功。长期项目按阶段收口，有限项目逐项核对目标后才建议结项。
6. **交付与恢复。** 给用户结果入口、实际验证、剩余风险/未验收范围和必要使用方式。按授权写同一项目主件与检查点，重读确认；跨文件导航更新不声称原子事务。项目归档、公开发布、发送及知识记录分别判断授权，不因验收通过自动执行。

## 质量与失败修正

完成声明应可从条件回到当前产物与证据，也能从产物回到目标；没有被隐藏的必须项或未知外部操作。证据只够支持局部结论时说明局部范围，继续完成仍可执行的必需工作。

模拟正例：界面构建通过且宽窗可用，窄窗保存按钮被遮挡，相关条件判 failed，修复并重验后再关闭事项。反例：把“服务启动成功”当作“跨平台长期稳定”。边界例：研究排除了一个高风险假设且满足研究产物标准，可以完成研究事项，不要求其结论有利于项目。

公共 read/check/write 拒绝结构上无证据的关闭，并不验证证据语义；原文、程序输出和真实使用为判断依据。工具或环境不可用时保留 pending，继续可独立核对的条件。没有本基本功专有持久偏好或跨项目状态；按公共 user-data 读取，验收正文保存在项目。

验证覆盖无证据完成、伪造/失效入口、局部测试、遗留必需项、阶段与事项分离、取消依赖、并发写入、保存重开和提前交付。既要观察错误完成是否被拦截，也要检查有充分证据的成果是否可顺利收口。方法效果仍需独立会话与实际项目验证。

## 项目归档与物理恢复

业务完成、取消、暂停与归档是不同事实。已验收不自动归档；只有明确归档/恢复授权才执行。复工的业务安排由推进控制负责，此处持有安全移动、入口核对与恢复方法；本项同时负责基线、实际操作、入口验证及可核实的本次补丁回退。

### 执行与核对

按当前 [project CLI](../../../docs/cli/project.md)和 [repository CLI](../../../docs/cli/repository.md)操作。项目档案位置固定为 `档案/项目/<项目名>/`，个人、企业与知识的业务分区可自行组织。只在明确要求范围归档，短期暂停或长时间未改动不自动触发。

1. 读取实例档案规则与唯一根卡，核对结果、归档原因、成果及未结事项；业务完成、中止或搁置由实际结案说明保存，不从 status 推断。
2. 预览 `project archive <name> --reason <说明> --dry-run --json`，核对目标、库存、字段变化和 referenceReview；冲突、工程嵌套及不支持的资源先报告，不覆盖、不自动合并。归档程序保留普通文件和层级，仅移动项目记录，不移动工程。
3. 实际操作后，按回执检查新位置、archive_history、repositories 和有效 Markdown 引用；只审阅并修复本次受影响的有效 Markdown/Wikilink。特别核对移出目录的相对链接、其他项目卡、knowledge.md、archive.md、资料导航和档案.md 的引用；必要时限定检索旧前缀。历史 JSON、来源表述及原始历史记录不做全局文本替换，用迁移说明交代位置。
4. 用新 scope 重读、check 及 repository check，核对文件完整与必要入口。程序完成不证明全部链接或业务事实正确；入口未核验不能报告整项完成。相关根卡及档案说明只持有分区入口，不复制完整清单。
5. 调阅用 archived scope，不自动恢复。恢复先预览再实际 `project restore`，默认 active，可指定其他状态；更新对应有效入口，核实最新事实与下一步。归档和恢复往返保留原件、正文事实和工程历史。旧项目若只在当前目录标记 archived，按明确复工请求用普通 project write 更新状态，不把 restore 无变化当作已激活。
6. 中断或部分失败按回执操作 ID 用 `project recover` 预览并回退程序变更；执行者另核对本次入口补丁。后续修改存在时保留现场，不强制覆盖或宣称跨文件原子回滚。锁持有者与恢复日志须实际核对，不能清理仍活动的写入。

项目删除另行核对明确授权：`project remove` 会删除整个项目目录及材料成果，须先预览实际范围，不因结项、归档或清理入口自动执行。工程正文及 Git 历史保持原位；确需删除工程时按独立任务处理。
