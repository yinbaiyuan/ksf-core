# 四层检查表、11 项必做检查与 10 条禁止事项

> 什么时候读：B 模式（体检）与 C 模式（处方）必读。逐层扫描 → 逐条检查必修与红线 → 按末尾模板出报告。
> 一句话：拿这张表逐项检查一个技能，每项给出结论并附上证据。
> 优先级：P0 = 致命，不修不能用；P1 = 重要；P2 = 可优化；P3 = 锦上添花。
> 判定写法：✅ 通过 / ⚠️ 部分做到 / ❌ 缺失；这一项和该技能无关时写 N/A（不适用），并说明理由。
> 编号写法：引用时带上前缀，如"必修 P0-3""红线 P0-1"，避免两张表的同号条目混淆。

## 四层架构依赖表（总览）

| 图层 | 喻体 | 解决什么 | 依赖 |
|---|---|---|---|
| 1 身份与加载 | 感官/入口 | 何时触发、协作授意 | 无（系统原生） |
| 2 逻辑与智能 | 大脑/中枢 | 如何思考、确定调性 | 依赖层1的上下文 |
| 3 执行与工具 | 手脚/末梢 | 物理产出、确定性 | 依赖层2的策略 |
| 4 资源与支撑 | 基座/骨血 | 知识储备、规范范本 | 横向支撑 1/2/3 |

用大白话说：
- 第 1 层：会不会被 AI 想起来、开工前有没有先跟用户对齐；
- 第 2 层：AI 怎么想、按什么标准做；
- 第 3 层：AI 怎么动手，会不会做错或乱改；
- 第 4 层：有没有参考资料和样板可用。
前一层没做好，后一层通常也会受影响；第 4 层给前三层提供材料。

## 图层一：身份与加载（Identity & Trigger）

| 模块               | 优先级    | 要求                                                                      | 一句话判据                   |
| ---------------- | ------ | ----------------------------------------------------------------------- | ----------------------- |
| YAML Frontmatter | **P0** | description = 身份 + 三个触发场景 + 独家资源 + 产出属性；≤100 词；必须写清使用时机，正文也可以补充，但不能代替 description 的触发说明 | 用 20 条应触发问题测试，能否被 AI 自动调用 |
| 初始对话协议           | **P0** | 多步任务第一步必须停顿确认："我计划分 X 步，预期产出 Y，是否开始？"                                   | 拿到一句话会不会直接狂奔，没确认需求就直接开干 |
| 决策树              | P1     | 多分支输入（本地文件 vs URL、类型分叉）必须有 if-then 路径图                                  | 模糊输入时 AI 知不知道走哪条路       |

## 图层二：逻辑与智能（Logic & Brain）

| 模块        | 优先级    | 要求                                                                           | 一句话判据          |
| --------- | ------ | ---------------------------------------------------------------------------- | -------------- |
| 核心执行原则    | **P0** | 潜意识护栏（让 AI 默认遵守的底线规则）；强力谓词定调性（用具体、有力度的词定下风格，如 Pristine 一丝不苟、Meticulous 极其细致） | 有没有"AI 塑料感"的口子 |
| 分阶段工作流    | P1     | 每个 Phase 有明确 Exit Criteria；禁止 Phase 1 就写正式产出                                 | 长任务会不会注意力溃散    |
| 质量标准与挑刺审计 | P1     | 交付前强制自检："列出 3 个可能缺陷，至少修正 1 个"                                                | 交作业前有没有自我博弈    |
| 哲学驱动层     | P2     | 审美类项目先出宣言（~500字），实现必须 100% 呼应                                                | 作品有没有灵魂        |

## 图层三：执行与工具（Execution & Tools）

| 模块      | 优先级    | 要求                                                    | 一句话判据                              |
| ------- | ------ | ----------------------------------------------------- | ---------------------------------- |
| 黑盒脚本封装  | **P0** | 非文本操作（图像/二进制/网络/旋转合并）必须锁死在 scripts/；AI 只读 --help 不读源码；纯文字流程写 N/A | 易翻车逻辑是否裸奔在提示词里                     |
| 外科手术式编辑 | P1     | 长文档修改只许 str_replace 级补丁，严禁全量重印                        | 会不会 Token 熔断（内容太长，把 AI 一次能处理的容量撑爆） |
| 侦察-响应   | P1     | 动态环境先截图/读 DOM/探测状态，所见贴入思考后再动                          | 有没有盲猜选择器                           |

## 图层四：资源与支撑（Resource & Assets）

| 模块              | 优先级 | 要求                                                | 一句话判据           |
| --------------- | --- | ------------------------------------------------- | --------------- |
| references/ 离线库 | P1  | 巨量规则/API 规格/黑名单外置；>10k 字文件配 grep 检索模式（按关键词搜索定位）   | 主文件是否清爽（建议少于 500 行，不单凭行数判定不合格） |
| examples/ 满分样本  | P1  | "满分作业"实体样本，搬运结构而非内容                               | AI 知不知道"好"长什么样  |
| 自动化评估           | P2  | QA 题集/validate 脚本，出厂前可回归（改完后能重跑旧测试，确认没把原来好的地方改坏。） | 是不是"我觉得好"式交付    |

## ✅ 11 项必做检查（必修 / To-Do）

| 条目编号（含优先级） | 动作 | 核心逻辑 |
|---|---|---|
| 必修 P0-1 | YAML 描述 SEO 强化 | 决定被点将的概率；触发词 + 场景 + 资源 + 产出 |
| 必修 P1-2 | 外科手术式编辑指令 | 保上下文的命根子；只传 diff 补丁 |
| 必修 P0-3 | 初始对话协议 | 心理契约；先对齐再动手 |
| 必修 P1-4 | 引用库离线化（行数建议少于 500 行） | 主文件只留流程，知识进 references/；不单凭行数判定不合格 |
| 必修 P1-5 | 分阶段退出条件 | 每关有哨兵，过关有硬标志 |
| 必修 P1-6 | 侦察优先 | 没看到的 = 不存在；先截图/读文件再行动 |
| 必修 P0-7 | 黑盒执行协议 | 涉及脚本时只看用法、运行脚本，不读源码；纯文字流程写 N/A |
| 必修 P1-8 | Few-shot 审美锚点 | examples/ 放样板房，设定质量上限 |
| 必修 P2-9 | 自动化校验闭环 | 交付前跑 validate，按报错递归修正 |
| 必修 P2-10 | Grep 精准提取 | 万字 reference 配检索词典，禁止全读 |
| 必修 P3-11 | 递归"读者"验证 | 模拟无记忆新实例读产出，有疑惑即回滚 |

## ❌ 10 条禁止事项（红线 / Not-To-Do）

| 条目编号（含优先级） | 禁忌 | 后果 |
|---|---|---|
| 红线 P0-1 | 严禁创建 README/INSTALL/CHANGELOG 等人读文档 | 无效噪音，机器库不需要客套 |
| 红线 P0-2 | 严禁对话式废话/独白 | Token 浪费；正文只能有规则、指令、代码 |
| 红线 P0-3 | 严禁猜测环境状态（路径/ID/页面） | 鲁棒性杀手；没侦察过 = 不存在 |
| 红线 P1-4 | 严禁模糊形容词（Beautiful/Good/Smart） | 审美偏差；改用具体参数或对标 |
| 红线 P1-5 | 严禁硬编码巨量数据在主文件 | 主文件膨胀；数据走 references/assets |
| 红线 P1-6 | 严禁单次全量重印长文 | 回声灾难，Token 熔断 |
| 红线 P2-7 | 严禁非标字符/美化过度 | 技术环境兼容性 |
| 红线 P2-8 | 严禁无反馈一股脑生成 | 方向性毁灭；关键决策点设人类中断器 |
| 红线 P2-9 | 严禁擅改核心脚本 | 确定性丧失；脚本标记 Read-only |
| 红线 P3-10 | 严禁单人独舞式生成 | 盲区风险；引入第二人称审计博弈 |

## 体检报告模板（B 模式产出物）

```markdown
# Skill 体检报告：<技能名> · <日期>

## 一句话结论
<这个技能现在能不能放心用？最该先修的 1 件事是什么？>

## 一、检查的是什么
- **检查对象**：<技能文件夹路径>
- **规模**：正文 <N> 行，另有 <X> 个附属文件（参考资料、脚本、样例等）
- **技能类型（主导范式）**：<编号·名称>，例如“3·协同共创 Partner”
- **结构选得合不合适（匹配度）**：高 / 中 / 低 —— <一句话说明理由>

## 二、逐层检查（四层扫描）

结论写法：✅ 做到了 / ⚠️ 只做到一部分 / ❌ 没做到 / N/A 不适用（必须写理由）

| 检查哪一层 | 检查项 | 结论 | 依据（第几行，原文怎么写） |
|---|---|---|---|
| 1 会不会被调用、开工前有没有对齐 | <检查项> | ✅/⚠️/❌/N/A | <行号 + 原文摘录> |
| 2 AI 怎么想、按什么标准做 | ... | | |
| 3 AI 怎么动手、会不会做错 | ... | | |
| 4 有没有参考资料和样板 | ... | | |

（每个检查项写一行，不能跳过；没问题也要写 ✅ 并给出依据。）

## 三、有没有踩中禁止事项（红线扫描）

| 编号 | 踩中了什么 | 依据（行号 + 原文） | 严重程度 |
|---|---|---|---|
| <如“红线 P0-3”> | <一句话说明> | <...> | P0 / P1 / P2 / P3 |

（一条都没踩中，就写“未发现违反禁止事项”，不要留空。）


## 四、总体情况（评级）
- **致命问题（P0）**：<N> 项没做到。不修就不能放心用。
- **重要问题（P1）**：<N> 项做得不够。
- **踩中禁止事项**：<N> 条。
- **量化数据（有数据才填，没有就写“未测”）**：
  - 该用时能不能被调用（触发准确率）：<数值 / 未测>
  - 占用多少文字量（Token 占用量）：<数值 / 未测>
  - AI 能独立做到哪一步（自治等级 C/B/A/S）：<当前等级>

## 五、修改建议（处方建议）

这里只列建议，体检阶段不改文件。确认要改时，再进入 C 模式（处方）逐条修改。

1. **[P0]** <对应编号或图层模块，如“必修 P0-3”>：<问题是什么> → <怎么改，只动最小范围（最小 diff）>
2. **[P1]** ...

（按严重程度排序；P0 最多列 3 条，先修最要命的。[P0]/[P1] 表示严重程度，不是条目编号。）
```
