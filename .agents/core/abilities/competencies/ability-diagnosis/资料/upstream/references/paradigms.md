# 七大架构范式与选型决策树

> 什么时候读：A 模式（创建）选技能结构时。
> 一句话：技能的结构要跟任务性质匹配，能简单就别复杂。
> 来源：官方 300+ 核心技能库的行为逻辑审计归纳。范式（=技能的组织方式）可以混用，但必须指定 1-2 个**主导范式**，并说明护栏（限制规则）。

## 范式总表（复杂度从低到高）

| #   | 范式               | 像谁   | 复杂度   | 文件结构                                     | 工作方式                                          | 代表案例                             |
| --- | ---------------- | ---- | ----- | ---------------------------------------- | --------------------------------------------- | -------------------------------- |
| 1   | 分拣路由 Navigator   | 分拣员  | ★☆☆☆☆ | SKILL.md 很短 + 大量 references/ / examples/ | 判断用户要哪一类 → 找到对应文档 → 按规范照办                     | internal-comms, brand-guidelines |
| 2   | 黑盒工具链 Operator   | 操作员  | ★★☆☆☆ | 纯文本任务可用 Markdown 固定流程；非文本操作配 scripts/ | 把用户的模糊说法 → 转成明确参数 → 按固定步骤执行（涉及非文本操作时运行脚本） | slack-gif-creator, pptx, xlsx    |
| 3   | 协同共创 Partner     | 合伙人  | ★★★☆☆ | 纯文字、不写代码，分多个阶段（多阶段 Workflow）             | 关键节点必须等人确认；先发散再收敛，循环几轮                        | doc-coauthoring                  |
| 4   | 双步创构 Philosopher | 哲学家  | ★★★★☆ | 一份"灵魂"文件（设计宣言）+ 正文，分两步                   | 先抽象哲学（Soul）→ 再具象表达（Body），宣言是渲染唯一合法依据          | canvas-design, algorithmic-art   |
| 5   | 侦察行动 Scout       | 侦察兵  | ★★★★☆ | 决策树 + 侦察动作                               | 先观察环境 → 拿到反馈 → 动态调整 → 再执行                     | webapp-testing                   |
| 6   | 元工程化 Architect   | 总建筑师 | ★★★★★ | 初始化脚本（init）+ 校验脚本（validate）形成闭环          | 指导、搭建、测试、验证另一个复杂系统                            | skill-creator, mcp-builder       |
| 7   | SDK 联动 Linker    | 调度中枢 | ★★★★★ | 容器化挂载、高度程序化                              | 通过 SDK/API（程序接口）动态装卸技能，在受控沙箱里执行，并接入运行监控（可观测性） | Agent SDK, Console Skills        |

## 选型决策树

```
这个任务的本质是什么？
├─ 查找/搬运已有的规范（分支多）
│    └─ 范式1 Navigator（SKILL.md 只写"什么情况去读哪份文档"）
├─ 用户说法模糊，但要按明确参数和固定步骤执行
│    └─ 范式2 Operator（纯文本任务可用 Markdown 流程；非文本操作配脚本）
├─ 好不好要靠人判断、需要来回几轮才能定稿
│    └─ 范式3 Partner（分阶段 + 每阶段有严格的过关标准 Exit Criteria）
├─ 产出要有"灵魂"/审美上限要求高
│    └─ 范式4 Philosopher（先写宣言、再做作品，两步分开）
├─ 环境会变，必须先看清再动手
│    └─ 范式5 Scout（先侦察，禁止盲猜）
├─ 要做的东西本身就是复杂系统（还要能自我验证）
│    └─ 范式6 Architect（初始化 init / 评估 evaluate 形成闭环）
└─ 无人值守、程序自动调度、大规模集群
     └─ 范式7 Linker（SDK / 容器 / 运行监控）
```

## 选型护栏（限制规则）

- 主导范式 ≤ 2 个；混用时写清每个范式负责流程的哪一段。
- 范式 1-3 的纯文本流程可以用 Markdown 实现，范式 2 不因范式名称而强制配脚本；涉及图像、二进制、网络等非文本操作时，仍按 checklist.md 的执行约束配 scripts/。范式 5/6 必须有 scripts/ 脚本；范式 4 必须有独立的宣言文件或段落；范式 7 通常超出单机skills的能力范围，谨慎承诺。
- 宁简勿繁：范式 1 能解决的，就不要上范式 3；复杂度每多 1 星，维护成本翻倍。
- 最后要定型：在 A 模式蓝图里写清"主范式 + 选它的理由 + 固定/可变合约"（哪些必须锁死、哪些允许 AI 发挥）。
