# 评测闭环（Eval Loop）

> 什么时候读：A 模式（创建）做完新技能（Skill）后；C 模式（处方）大改之后。简单或纯主观的技能可以跳过（与官方口径一致）。
> 一句话：别凭感觉说"技能变好了"，拿同样的题让"用技能"和"不用技能"各跑一遍，用结果说话。
> 前置条件：§3 如果要借用官方 skill-creator 的 `agents/` 提示词，本地需要装有该技能；没装就用聊天内评审代替，方法本身不受影响。

## 一、效果评测（用技能 vs 不用技能，对照着比）

1. **出 2-3 条真实测试题**：要像真用户会说的话（可以有错别字、口语、具体文件名），先给用户过目。
2. **同一轮里同时派两组子代理（subagent）**：A 组拿到技能路径，要求按技能执行；B 组不用技能，直接做同样的题（裸跑）。如果是改版场景，B 组改跑旧版本的快照。
3. **产出存进工作区**：`<skill名>-workspace/iteration-N/<测试名>/{with_skill,without_skill}/`，每组记下 Token 占用量和耗时。
4. **写断言（assertions，可判对错的检查点）**：趁子代理还在跑时起草。必须能客观判断（比如：文件存在、字段正确、格式合规）；"写得好不好"这类主观质量交给用户判断。每条断言起一个人能看懂的名字。
5. **打分**：逐条判断通过/不通过（pass/fail），并留下证据（能写脚本验证的就写脚本，不靠肉眼看）。
6. **汇总成对比表（基准表）**：

| 配置                             | 通过率 | Token 占用量（均值±波动） | 耗时  |
| ------------------------------ | --- | ------------ | --- |
| with_skill（用技能）                |     |              |     |
| without_skill / old（ 不用技能或旧版本） |     |              |     |
| Δ 提升（两者的差值）                    |     |              |     |

7. **人工评审**：没有浏览器评审页面时，就在对话框里逐个展示“题目 + 实际产出 + 打分”，由用户逐条反馈。网页展示是可选项：如果本地已安装官方 skill-creator，并确认其中的 `eval-viewer/generate_review.py` 存在、支持 `--static`，且运行环境和输入数据符合要求，可以用它生成评审网页；不具备这些条件时，继续在对话框里评审，不必为此安装工具。网页只负责展示，不能代替实际测试和用户判断。
8. **迭代**：按反馈改技能 → 进入下一轮 iteration-N+1（也要把对照组重新跑一遍）→ 直到用户满意，或者反馈全部清空。

## 二、触发评测与描述优化（手动版"描述优化器"）

要解决的问题：技能该用时 AI 没想起来。本轮只测应触发场景的成功调用率，不衡量误触发情况。

> 原理：AI 有"该用却没用"的倾向（欠触发），所以 description 要写得主动一点（pushy）；而且 AI 只在遇到"自己搞不定的复杂任务"时才会去查技能——太简单的问题测不出触发效果。

1. **造 20 条应该触发的测试问题**：覆盖技能的使用场景，同一个意图换多种说法（正式的、口语的、不点技能名的）；不加入不应该触发的反例。
2. **用户过目**后，存成 `evals/trigger-eval.json`。
3. **每条跑 3 遍取稳定结果**（每条问题开 3 个新会话或子代理）；按 60/40 把题目分成"训练集"（用来改）和"保留集"（用来检验）。
4. **在 ≤100 词的范围内改 description → 只看保留集的分数挑最好的版本**，防止只在练习题上表现好（过拟合）；最多改 5 轮。
5. **采用**：确认 description ≤100 词后，把最好的版本写回技能顶部的 YAML 区（frontmatter），报告修改前后的分数。

## 三、盲测对比（可选，重要技能才用）

把两个版本对同一任务的实际产出标成“结果 A”和“结果 B”，不要告诉评审子代理哪个是新版、哪个是旧版，也不要透露自己的偏好。将原任务、相同的评价标准和两份产出交给独立子代理，让它比较并给出依据；再分析两份结果的差异。

skill-creator 提供了三类评审提示词：grader（检查和打分）、comparator（比较结果）、analyzer（分析差异）。如果本地已安装该技能，可以读取 `agents/{grader,comparator,analyzer}.md`，确认所需输入和工具适配后再借用。它们是可选参考，不是做盲测的必需文件；没有这些文件时，仍可依据原任务和评价标准组织评审，不能声称使用了官方提示词。当前环境不支持子代理时，改为在对话框里交给用户评审。

## 四、升级铁律

- **从反馈里找共性，别只为这几道题打补丁（防过拟合）**：技能要服务成千上万次调用，不是只为了通过这几道测试题；顽固问题就换个比喻、换种做法，别一味堆"必须（MUST）"。
- **保持精简**：删掉不起作用的指令；不仅看产出，也要看 AI 的执行过程记录（transcript）——发现技能让 AI 白忙活，就砍掉那一段。
- **解释 why 优于堆 MUST**（新官方哲学，与老宪法"纯祈使"的裁量）：**低自由度机械段**（脚本调用、格式、安全红线）保持硬祈使零解释；**高自由度判断段**（何时收敛、为何如此设计）写清 why，让模型理解后自行泛化。满篇 ALWAYS/NEVER 大写是黄旗。
- **重复劳动→收编脚本**：3 个测试里 subagent 各自写了同款脚本 = 强信号，固化进 `scripts/`。
