# 设计原则与底层原理

> 什么时候读：A 模式（创建）开工前定调；或需要向用户讲清"为什么这样设计"时。
> 来源：官方 300+ 技能审计 + 官方 skill-creator 文档对比提炼。

## 三大底层原则

### 原则一：能省就省（节制的美学 / Concise is Key / Token Economy）

一句话：只写 AI 不知道、又会影响结果的内容。

- 上下文窗口是公共资源：skills技能要和系统提示、对话历史、其他技能元数据共享窗口。
- AI 已经很聪明：只补它不知道的背景。每段文字都问一句："这段值得占用这些Token吗？"
- 不写常识：不解释"什么是 PPT"，只写"在这个具体场景下，它应该长什么样"。
- 用命令句，不用商量语气：删掉"我认为最好是……"，直接写"创建文件……"（Create the file...）。
- 相比冗长的解释，更偏爱简洁的示例（Show, don't tell）。

### 原则二：该严格的严格，该放开的放开（自由度匹配 / Degrees of Freedom）

一句话：越容易出错的步骤，越要限制 AI 的发挥空间。

先判断任务属于哪一种：
- "悬崖上的窄桥"：一步走错就出事 → 加强护栏；
- "开阔的平原"：需要创意、怎么走都行 → 放手探索。

| 自由度 | 怎么控制 AI | 适用 |
|---|---|---|
| 高 | 文字引导、给灵感方向 | 文案、哲学、头脑风暴 |
| 中 | 给模板，让 AI 只填空位（`str_replace` 定点替换） | 报告、表格、固定格式产出 |
| 极低 | 写成脚本（放 scripts/，AI 只负责传参数并运行） | 精确旋转 PDF、打包编译、二进制文件操作 |

配错就出事故：危险任务给了高自由度 → 结果不稳定（鲁棒性差）；创意任务被锁死 → 浪费 AI 的能力。

### 原则三：先补背景，再分层存放（前置认知与解耦 / Cognitive Grounding）

一句话：别假设 AI 知道你知道的事；按"多久用一次"决定内容放在哪。

- 知识的诅咒（Curse of Knowledge）：写skills的人默认读者懂背景，但通用 AI 什么都不知道。
- 需要和用户深度协作的技能，严禁拿到一两句话就开干：必须先有"收集信息与背景"这一步（即初始对话协议）。
- 分层存放（解耦）：每次都要读的 → 放 SKILL.md；偶尔才需要读的 → 放 references/；不用读、只需运行的 → 放 scripts/。

## 技能分三级加载（渐进式披露）

为什么要分层：AI 不会一次读完整个技能包，而是用到哪层才读哪层。

1. **L1 元数据（name + description）**：常驻上下文，约 100 词内。决定 AI 会不会想起调用这个技能。
2. **L2 正文（SKILL.md）**：触发后加载。< 5000 字，建议 < 500 行。
3. **L3 资源（references/ scripts/ assets/）**：按需加载或根本不进上下文（脚本直接执行）。

## 长度规则（100 词 / 5000 字上限，500 行为建议）

- description ≤ 100 词：写清 我是谁 + 三个使用场景的触发短语 + 独有资源 + 产出物特点；超过时压缩措辞，不能以补充场景为由突破上限。
- SKILL.md 正文 < 5000 字：超过字数上限时，把细节挪到 references/，主文件只留"何时读它"的索引。行数建议少于 500 行，但不因行数达到或超过 500 行就单独判定不合格。
- references/ 单个文件 > 10k 字：必须在 SKILL.md 里写好检索关键词（grep：按关键词搜索定位），让 AI 只读相关段落，禁止整篇通读。

## 去掉"AI 塑料感"（Anti-Slop，审美层）

"塑料感"指 AI 默认写出的那种空泛、套路、哪里都差不多的内容。

- 好技能（Skill）的最高境界不是写一套流程（SOP），而是**排除平庸选项**（概率裁剪）：明确禁止那些"安全但平庸"的写法，把 AI 推向高水准输出。
- 顶级skills会给 AI 注入性格：挑剔、较真、有立场（见 templates.md 的禁用词表）。
- 审美要求要写成能判断对错的规则（具体参数如正文使用 12pt 字号，或具体对标如"像 Stripe API 文档那样 / Like Stripe API docs"），不要只写"好看"（Beautiful）。
