# 系统发行

## 结果与输入

输入为 Core 根、版本配置、精确源码来源、目标平台、输出目录、验证结果及构建或发布授权。结果是可检查的本地发行产物，或已核对远程状态的正式发行；两者不能混称。实例本地编辑应先经贡献或明确的 Core 开发任务进入系统源，不整体推送个人历史。

## 方法与失败处理

1. 读取[Git 规则](../../../docs/git.md)，核对 Core 身份、分支、已有差异、构建配置及随包平台。版本来自 build.json，不自动递增，不手填 manifest 或 release.json。缺少版本决定或纯系统来源时不得宣称可正式发布。
2. 通过 `.agents/ksf build --json` 生成运行声明，执行 `.agents/ksf test` 和 `.agents/ksf runtime verify --json`，修复受影响失败。现有检查不证明所有 Agent 行为已测试，分别记录实际覆盖。
3. `release build --output <目录> --json` 构建 Core 包、workspace 包、模板目录和索引。普通正式包要求干净来源；本地试验可显式 `--allow-dirty`，所得 development 包不得用于正式发布或公共更新源。检查产物、平台、版本、来源提交、大小与摘要；模板和实例只保存小型发行凭据，更新包保留文件校验清单，不内嵌原版正文，不额外生成原版快照。隔离验证模板首次启动。
4. 仅要求构建时到此交付。要求发布时先 `release publish <目录> --dry-run --json` 展示确定产物和目标；已有有效发布授权时执行实际命令。`--release-only` 只发布 Release，模板由现有 CI 后续同步；必须把两者状态分别报告，不能说模板已同步。
5. 模板同步使用 `release template <目录>` 或 `release mirror`。核对远程模板来源和版本；旧版不得覆盖新版，同版本不同提交拒绝。同版本同来源可重复核对并修复模板树，更新分支必须非强制，竞争失败先重读远程，不覆盖别人的提交。
6. 上传或响应不明时，按原版本和产物重试对账：既有 tag、资产摘要必须一致，已正式发行资产不可替换。模板失败可能留下草稿 Release；如实说明部分状态，不能为重试而删除未知远程产物。

## 验收与边界

本地交付列产物、版本、来源、摘要与测试证据；正式交付增加真实 Release 链接、资产状态、模板实际版本与提交、未决项。凭证只按现有工具契约取得，不进入产物或日志。当前实际发行平台为 macOS ARM64，Windows 恢复契约不代表完整平台支持。

模拟正例：干净来源构建并验证后，经明确授权发布相同资产。反例：把 allow-dirty 产物当正式版、模板尚未同步就宣称发行链路全部完成。边界例：模板已更新到更高版本，拒绝旧任务回写。依据[release CLI](../../../docs/cli/release.md)、[发行协议](../../../docs/distribution.md)与程序测试验收；真实远程发布与模拟 API 分别标注。
