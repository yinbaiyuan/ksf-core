# 责任怎样成为可用搭档

归属：搭档设计。新建、整体重构及职责争议时读。

## 从服务关系而非称号出发

搭档承接的是反复出现的责任。先确定使用者、问题情境、用户希望的结果和失败代价。“采购专家”“学习教练”只是线索；没有具体服务和成果，无法确定该问什么、用什么方法或怎样结束。

持续责任不意味着必须后台运行、周期唤醒或跨会话自动记忆。它可以由当前 Agent 在需要时承担，继续能力取决于实际记录和宿主机制。

## 责任、方法、资源分开建模

责任说明必须得到什么结果、谁负责检查；方法说明如何完成专业处理；资料说明可用事实及来源；工具说明真实操作能力和条件。

一个责任可以组合多个方法，一个方法也可以支持多项责任。不要为了画齐一对一映射给每个小动作造基本功。通用 Agent 能直接完成的组织动作可在搭档中说明；可独立复用的专业判断应由方法持有。

方法输出不自动等于搭档交付。搭档要检查各产物是否共同满足用户目标，处理遗漏、冲突和需要用户选择的取舍，不能重新发明专业标准覆盖方法结论。

## 用承接闭环界定边界

对于每项必需责任，追问：输入从哪里来、如何处理、处理不了怎么办、交什么、由谁确认或继续使用。任何断点都会使角色看似完整却无法接任务。

边界不是列长串“不负责”。重点描述何时接手、什么时候需要另一责任、带什么交出去以及回来后怎样继续。跨多个独立搭档的可复用合作规则归协同。

## 角色、模式和新对象

同一服务责任采用不同方法，通常保留为一种搭档的不同路径。若服务对象、成功标准、需要独立承担的责任明显不同，比较拆分；仅因材料多、工具新或提示词长不足以新增。

角色过宽时先找互相冲突的成功标准和独立交付，而不是机械按主题拆分。角色过窄时检查它是否只是一个方法的另一个名字。

## 交互服务于工作

提问应解决具体未知，反馈应让用户能评价具体候选。已有事实和授权直接复用；普通组织选择由 Agent 完成。不要规定必须问若干题、必须经过几轮或每一步等同意。

分析任务需要区分事实、假设与判断；训练任务必须有实际作答和反馈；制作任务需要成品；管理任务需要明确对象和处理结果。角色称号不能代替这些证据。

## 可继续的原件

工作底稿是本次设计、证据、练习或决策的原件，不是搭档的私人设置。说明原件入口与需要恢复的内容，沿 Runtime 和对应管理方法使用现有记录。

长期设置只保存本搭档真正消费的偏好或必要状态，不保存整段成果、不隐式继承基本功参数、不因观察到一次表达就自动记为偏好。
