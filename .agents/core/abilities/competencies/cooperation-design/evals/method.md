# 协同设计评估方法

归属：协同设计。

依据 cases.json 的整体目标、初始输入和给定参与定义，按本包独立设计。先保存合作方案和完整候选，再走实际主路径、失败与变化路径；原件位置、输入版本、接手判断、返回及最终结果必须可读。

可用同一 Agent 顺序承担不同责任进行情境执行，但应明确这种执行范围；不能据此声称真实多 Agent 并发或多人协作效果已验证。模拟案例身份与真实项目结果分开。

逐项检查 criteria 和专业检查表。用既有程序检查对象、精确引用和加载；依赖是否可推进、交接是否足够和结果是否一致由案例评审判断，不用文本关键词代替。

上游变化测试至少指明变化输入及一个直接受影响结果，并检查其后续使用者；不要求无关部分全部重做。循环失败题确认有明确协调及取舍去向。边界题应能拒绝把单搭档过程建为协同。

修复后只重跑失败与受影响邻题，当前范围的阻断问题解决、结果和限制清楚时结束。后续独立模型对照复用题库并记录真实运行指标。

trigger-eval.json 的应调用和不应调用分别核对；没有真实自动调用记录时不填写触发率。自举以元能力组合为案例，检查是否强行要求每次走完所有设计及额外维护中枢。

## 触发评测执行约定

题库前12条应调用题用于调整描述，后8条保留；同一模型和工具条件下每题在新上下文运行3次，记录实际调用与原始结果。最多调整5轮，按保留题表现选优，不能只汇报训练题。边界题的误选单列，不混算应调用成功率。平台不能观察真实调用时只报告走查结果。

## 后续独立模型对照

使用同一输入、支持和标准，让独立上下文分别按新版与旧版（或不用本方法）完成任务，保存原始产物、实际执行、耗时及可取得的消耗。能机械判定的条件用程序，专业设计及取舍由明确评审者检查；有条件时隐藏版本标签。当前会话演示与这种对照分开记录，不能因题库已有标准就预填效果。
