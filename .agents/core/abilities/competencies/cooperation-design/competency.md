# 协同设计

## 职责

设计多个独立责任共同完成一类结果的协作规则。交付完整协同定义及其成果依赖、接手条件、协调和返工办法、整体完成条件与验证材料。

普通协同须同时有独立责任、必要的合作关系和可复用价值。一个搭档内部步骤多、工具多或材料多，不能单独成为协同理由。现有根 AGENTS.md 是特殊入口，仅在明确修改入口时按其固定契约设计。

## 核心工作

1. 从整体交付和成功条件出发，确认需要哪些独立责任及合作。可以复用已有流程或留在单个搭档内部，不强制创建协同。
2. 给成果和关键决定明确责任方。专业方法由参与搭档及基本功持有，本协同定义谁交什么、何时接手及怎样判断交接有效。
3. 按成果输入关系选择顺序、条件、分支汇合或反馈结构。只有输入充分、结果独立且不竞争同一原件时才并行。
4. 定义关键交接：成果原件和版本、依据与未决、接手条件、不合格返回谁、接收后谁维护。需要的参与者未建成时明确缺口。
5. 定义分歧、上游变化和返工：识别受影响成果，保留未受影响部分；反馈要有改动依据和退出条件，不能无限互相退回。
6. 走查主路径、失败及变化路径，检查各责任完成后整体结果是否真正达标，再按本次要求交付或交能力维护落实。

细节由本包工作方法持有。定义合作规则不代表已经实际调用多个 Agent；执行方式沿宿主和当前工作安排。

## 产物底线

- 每项必需成果有人负责，关键依赖能确定“现在能做什么、还需等什么”。
- 接收方能据原件和条件继续，不依赖口头“上一位已经做好”。
- 有专业不合格、缺资料、冲突和上游变更的去向，不悄悄降低整体标准。
- 循环知道凭什么继续、何时结束、重复无进展时谁处理取舍。
- 整体交付能检查跨成果一致性，节点结束不自动代表业务完成。
- 流程参数仅在确有跨任务需求时设计；各参与对象消费自己的参数，进度和成果留在任务原件。

## 完成与自举

完整候选或本次审查结果已交付，必要参与者与缺口、案例结果和下一承接清楚时结束。没有合作必要时交付具体复用或单搭档承载建议。

设计协同设计自身的配合时仍用上述标准；不把三项设计机械串成每次必须全走的流水线，不为自检增加维护中枢。
