# 项目路由

## 职责

判断当前工作属于哪个项目，取得下一步需要的项目事实和工程入口，交回 Runtime。

已有归属和事实仍然有效时直接复用，不每轮重新匹配。Runtime 负责切换和工作绑定，能力路由负责选能力，项目管理及其方法负责建立、规划、推进、保存和归档恢复。

## 先取得必要事实

1. **先看已有或指定项目。** 已完整提供且仍有效的根卡直接复用，否则通过本实例启动器执行 `project read <目录名> --part all --json`。命令使用项目目录名，核对返回的实际 `scope`、`path` 和项目身份。

2. **需要找项目时才列举。** 执行 `project list --json`，先看标题、说明、状态和路径，再读可能相关的根卡，不批量读取全部项目。需要核对归档候选时，才使用 `--scope archived` 或 `--scope all`。

3. **沿明确入口补事实。** 继续具体任务时，读取相关管理主件、指定任务记录和实际产物，取得足以接续本步的原文。根卡概述不能代替重要事实；不因为资料可能有用就扫描整个知识库。多个未决任务不能凭修改时间猜选，完成或取消的事项不自动重开。

## 判断归属

| 当前依据 | 怎么处理 |
| --- | --- |
| 原项目仍适用，本次只是追问、补充或局部纠错 | 保留归属，只补受影响事实 |
| 用户明确指定，或项目目标、现行事项等事实明确指向一个候选 | 核对根卡后返回该项目及依据 |
| 只有名称相似、当前目录相同，或引用了该项目资料 | 作为线索，不据此确定归属 |
| 多个候选成立且会影响资料或写入位置 | 返回具体候选和推荐，交 Runtime 澄清 |
| 没有相关项目，且本次不需要长期项目 | 按无项目返回，不自动建卡 |
| 指定项目不存在，或读取失败 | 返回实际问题，不当作普通“无项目” |

一个工作只返回当前实际推进的项目。项目的父子关系不参与路由：推进子项目就返回这个子项目，推进总项目就返回总项目。只把明确用作资料的项目列为关联。明确切换时，返回新项目和仍有效的成果，由 Runtime 更新安排。

同名项目在 `current`、`archived` 下分别核实；当前目录中标为归档的旧项目也不默认作为活跃项目。归档调阅不代表复工。明确创建、恢复或维护请求交相应专业能力处理，读取项目不增加写入授权。

## 取得项目预设

没有 `routing` 就返回无预设；有配置时，执行 `project check <目录名> --json`；完整有效的检查结果已经提供时直接复用。读取和检查归档项目均使用实际 `scope`。

保留原始配置、实际根卡位置，以及每项有效或失效的结果和具体错误，交能力路由使用。这里不选最终能力，不加载全部预设正文或对象私人设置。

无效项保留原配置，不自动改版本或换来源。预设检查失败，仍保留已经取得的项目事实；可用性检查通过也不代表适合当前任务。

## 按需核实工程

本步需要工程事实或准备进入工程时，再沿根卡的 `repositories` 或已核实的正文链接确认入口，按需使用仓库接口读取、检查。

根卡中的相对工程路径按根卡所在目录解析；绝对工程路径在当前设备核实。进入工程前确认实际 Git 根、工程的 AGENTS.md、说明和 Git 状态。已经核实且没有已知变化的结果可以复用；目录、worktree 或设备变化后重核。

工程缺失或入口冲突时，返回具体问题，不在同名目录重建。新建、关联和解除工程交项目管理安排，工程源码和 Git 历史保持原位。

项目目标、决定和进展沿项目现行记录核对，代码及构建事实沿实际工程核对。来源冲突时说明具体差异和仍待核实的内容。

## 交回 Runtime

返回主项目及实际 `scope/path`，或明确的无项目、归属待定、读取失败结论；同时带上采用依据、必要原文及事实入口、预设检查结果、相关工程和规则位置、缺口及下一动作。

核对命令是否成功、结果是否完整及具体错误。完整空集合才表示没有候选；不完整、截断或读取失败不能冒充无项目。保留已经取得的事实，说明哪些部分可以独立继续。

项目事实足以支持下一步，或具体缺口和可继续部分已经明确，本步骤即完成。

例如：

- “继续上一版报价”：沿原项目补读本次需要的记录和产物，不重新匹配全库，也不因关联了仓库就检查工程。
- 两个项目关联同一工程：不能只凭当前目录决定归属。
- 引用其他项目案例：主项目不变，也不取得对该项目的写入授权。

接口参数不清时，按需查阅 [project CLI](../../../docs/cli/project.md) 和[工程 CLI](../../../docs/cli/repository.md)。
