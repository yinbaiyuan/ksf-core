# Git 协作规则

系统与个人数据以独立仓库和发行清单区分。`ksf-core` 是唯一系统开发源、模板与发行入口；真正的用户实例叫 `ksf` 或用户自定义名称，可以是私有仓库或普通文件夹。机制见[发行说明](distribution.md)。

## 仓库与分支

- Core 稳定主分支为 `core-main`，功能和修复分支按用途命名，PR 目标统一为 `core-main`。新系统分支必须来自已核实的纯系统历史。
- 用户从 Core 默认分支创建独立模板仓库；初始化后本地使用 `main`。模板没有 Core 的提交历史，分支名称不建立共同祖先。原 Workspace 不再参与创建或发行。
- 个人工作区使用自己的 main 和个人远程。升级按 Release 版本及基线执行，不整体合并 Core 分支，也不依赖个人 Git 历史。

## 内容归属

Core 承载 .agents 下的系统定义、程序、文档、测试和模板源，以及根 AGENTS.md、README.md、.gitignore 和 .github 协同。系统示例使用虚构数据。根协作文件的通用模板源位于 `.agents/core/distribution/template/`，发行与贡献只采用该系统源，不读取真实根文件。

真实实例根 USER.md、BOT.md，以及项目、知识、用户能力、收件箱、档案、随目标保存的原始资料及旧实例已有原件目录，以及 `.agents/user-data/` 系统级用户数据属于用户实例，Core 不跟踪这些用户目录或占位文件。个人实例的空目录由初始化程序或本地构建检查目录生成，不再创建根级源档目录，测试数据在临时目录创建。Core 的忽略列表采用系统源码白名单，防止本机用户内容误入库；用户实例使用模板自带的另一份忽略列表，允许正式个人数据入库，排除本机缓存和独立工程容器 repositories 等。两个列表各自维护，不按分支切换本机 Git 配置。

用户根的 `repositories/` 是工程容器，根 `.gitignore` 使用 `/repositories/` 排除整个容器；容器本身不初始化 Git，不使用子模块或父仓库 gitlink，各工程独立管理历史与远程。项目根卡保存入口，工程正文与历史不随父 KSF 仓库备份。已有工程原位关联，归档或删除项目记录不移动、删除工程。

用户已要求实际工程交付且缺少工作区时，可以通过 repository create 初始化默认工程；该动作不包含 Git 暂存、提交、推送或远程创建。关联和解除关联只改根卡。

升级不修改个人 Git 配置、远程或 .gitignore。首次 instance init 只在根忽略规则仍与已验证 Core 相同时采用实例规则，并将当前本地分支改为 main，不提交或推送。复制文件夹无需 Git。创建远程备份时优先从模板创建自己的私有仓库；公开上游的 fork 也会公开。

## 系统提交和推送

生成开发提交信息前，先读取并遵循[Git 提交信息规则](git-commit-message.md)，按其中的标题、正文、模板与证据要求处理。Agent 在定向暂存并审阅实际差异后生成说明，提交前执行 `commit-message check --from <完整消息文件> --json`，再核对说明与差异、验证记录一致。模板与格式检查不能替代语义核对。

任何 Git 写操作前检查当前分支、工作区和已有暂存差异。混合工作区只定向暂存授权的系统文件，不使用 git add .、git add -A 或 git commit -a。提交前审查暂存内容；用户目录及其占位文件不能进入系统提交。

推送前核对实际远程、源/目标分支和全部待发送提交，不只检查最后一个提交。不得向 Core 整体推送个人分支或混合历史。忽略列表不是权限隔离，已跟踪、强制添加和旧提交仍需审查。

用户要求普通项目、知识或能力维护，不自动授予提交和推送权限。明确的系统发行任务需要纯系统提交时，按该任务的实际授权实施并检查来源；本规则不引入另一轮无依据的确认。

## 用户贡献

生成 PR 说明时先遵循[PR 说明规则](pr-description.md)：共同标题沿用提交规则，Git 正文和 PR 正文分别生成、校验并冻结。PR 必须说明背景与目的、主要变更、验证结果及影响与兼容；破坏性变更补迁移与回滚。内容核对不能只靠模板或格式检查。

普通能力定制保存在用户能力区。用户实例中的系统修改须先形成该实例的本地 Git 提交，再用 contribute prepare 从最新 HEAD 与同一提交保存的正式 Core 基线比较，展示选定公开内容并按授权 submit reviewed 摘要。比较完整系统状态，包含多次本地提交的累积差异。暂存区、未暂存修改、未跟踪文件全部忽略，不要求整个仓库或选定文件的工作目录干净。贡献命令不自动 add、commit 或 push 个人仓库。

贡献计划 schema 5 分别记录本地 sourceCommit、精确 Core 来源基线和目标 core-main。旧来源 branch=main 保留真实含义，不决定新 PR 的目标。首次发布前 HEAD 改变须重新准备；仅继续编辑不影响计划。发送前先核对远程原版 Core 的选定文件与基线一致，再按[提交信息规则](git-commit-message.md)创建带完整正文的纯系统提交和 contrib-<ID> 分支。个人文件、个人提交说明、作者配置、Git 历史和本地提交标识不发送给 Core；公开说明由选定系统差异另行整理并冻结审阅。准备需要 Git、HEAD 和正式发行凭据，并联网读取凭据固定的原版 Core；本地 read 和 submit dry-run 不联网。公开 Core 可匿名读取，也可复用已有授权；实际公开需要账户授权。个人 main 的 origin 不能被默认当成系统发布目标。旧计划保留可读及已有 PR 只读核对，不能用于新发布。prepare 提示同一提交节点或相同系统内容的已有贡献；相同内容的新计划提交前只读核对并返回已有 PR，不重复创建。PR 已关闭、合并或远程状态未知时不得自动另开 PR，部分成功先恢复原贡献 ID。

创建草稿 PR 后，Agent 必须在最终回复中提供 PR 链接，并显式提醒：当前 PR 仍为草稿，准备送审时需要改为 **Ready for review**；用户可以在 PR 页面操作，也可以让 Agent 代为修改。复用已有 PR 且确认仍为草稿时，同样提醒，不能只报告“已创建草稿 PR”或 CI 状态。用户明确要求 Agent 转换状态时直接执行并核对结果，已有明确授权时不重复确认。

本规则不声称已安装全局 Git 钩子或配置服务器保护。强制检查范围以实际发行、贡献程序和验证结果为准。

## 官方根文件

公共 README、忽略规则、属性及官方工作流的规范源在 `.agents/core/distribution/repository/`。在个人实例中修改规范源，贡献程序将其显式投影为 Core 根文件，并把两份差异一起纳入审阅；不读取或上传用户根 README、.github 或忽略规则。升级只更新规范源。官方检查和发布均限制官方仓库运行；模板复制出的个人仓库不会执行官方发行。
