# SDK API兼容与双渠道升级

Core、SDK工具包、应用业务版本和业务数据格式分别管理。`schemaVersion:1`是清单格式，`sdkVersion:1`是运行协议代际；二者不因SDK API补丁或次版本变化而递增。

当前候选SDK为1.1.0，宿主声明`{version:"1.1.0",minCompatibleVersion:"1.0.0"}`。应用的`sdkApiVersion`必须位于这个闭区间；范围表示经验证的连续兼容承诺，不自动跨越破坏性主版本。构建器将实际工具包版本写入`sdkApiVersion`和`builtWithSdkVersion`，首版要求两者相同，不支持手填更低运行目标。新包的`minCoreVersion`至少为0.5.3，旧宿主会因Core下限而拒绝误装。

旧包缺少两个新增字段时，读取方按API 1.0.0解释，保留原始字节和摘要。旧包的Core下限、平台、Node ABI和业务数据检查仍然有效。SDK包版本、API导出、宿主数据兼容声明由构建检查核对；运行时协议副本及官方应用源校验器从SDK协议维护源同步。

安装、商店候选、启动、Core更新和两种回退均使用同一兼容判断。检查目标Core时读取目标的声明，不能套用检查程序自身支持的SDK范围；Node ABI从已经校验的目标运行时取得。旧Core没有API范围声明时按1.0.0解释。SDK兼容不替代业务数据格式兼容。

## 双渠道与版本选择

核心应用保持`ksf-apps`统一来源身份，Core离线包和公用源索引交付相同的不可变应用包。同一ID、版本、平台、ABI的包必须同摘要；构建或代码变化递增应用版本。发布准备只复制已经校验的包，不重打包、不覆盖旧版本。本地准备和HTTP验收不代表线上已发布。

Core更新预览列出应用更新、保留、安装、跳过和阻塞理由；阻塞回执保留逐应用计划和具体不兼容原因。较新的兼容安装或pending版本优先保留，较旧安装更新到适用随包版本；不把不兼容应用静默降级。用户停用、显式停止、安装身份和卸载意图保留，终端等非默认应用不因Core更新自动安装。独立业务应用也必须能在目标Core上运行。

实际Core切换前正常排空并停止主服务。不可变应用文件先准备，Core与安装指针在受版本保护的可恢复操作内切换。应用索引或根入口发生并发变更时停止，固定入口恢复只处理本事务的旧/新快照。0.5.2旧更新器首次安装新Core后，在新服务就绪前执行一次幂等随包对账，并关联原Core备份；同一次Core激活的后续启动不重复撤销用户的应用回退，经过新的Core事务再次激活时重新对账。

## 回退与数据

Core回退恢复本次切换持有的应用指针，保留之后的用户配置变化。后来经商店独立更新的应用在旧Core兼容时保留，不兼容时阻止回退。向不认识应用恢复记录的旧Core回退时，保留向后兼容的新版固定恢复入口，并在回执报告`recoveryLauncherRetained`；正式Core版本和原始来源凭据不改写。

单应用回退需有previous版本且无pending切换，核对目标SDK、平台、不可变文件和当前数据。代码回退不恢复旧业务数据快照；新格式不被旧代码支持时拒绝回退并保留原件。JSON迁移由应用显式执行，user和runtime数据均可能是持久业务或恢复状态。

日常实例运行未正式发行的本地候选时，保留正式安装凭据；关于页面区分执行的Core版本、正式安装版本及SDK API范围。公开发行、实例正式安装与本地候选验收分别记录。
