# 项目文档架构与治理指南

本指南解释项目治理能力与程序的文件架构，说明项目、里程碑、任务、上下文与两级复盘的职责和文档组织方式。适用于完成一件具体工作的轻量项目，也支持通过里程碑和子项目扩展到复杂项目。

业务定义由[项目管理能力原件](../../abilities/partners/project-manager/references/governance.md)持有，本文不承担定义或运行依赖；新格式字段、公共读写、校验和迁移见[项目治理文件协议与接口](governance.md)，可使用[正式模板](templates/README.md)。[旧管理主件](../project-management.md)和[旧检查点](../runtime/task-checkpoints.md)继续支持未迁移项目。存量项目手动调整目录和引用后，用公共校验检查切换结果。

## 结构与目录

逻辑关系：项目可递归拆子项目；每层项目有自己的方案及完成条件，通过一个或多个里程碑推进；每个独立任务在所属里程碑内有一个文件夹，简短任务文档和编号上下文同处其中。

项目根目录直接放项目主文、编号上下文、里程碑目录和项目复盘。每个里程碑目录直接放阶段主文、编号上下文、任务目录和阶段复盘。父子项目通过元数据关联，各自使用同一结构。

```text
项目/示例项目/
├── project.md
├── 灵感闪现.md
├── P00-项目背景.md
├── P10-跨阶段调研/
│   └── 原始数据.csv
├── M1-阶段结果/
│   ├── milestone.md
│   ├── M00-阶段共识.md
│   ├── M01-共用样本/
│   ├── A1-方案设计/
│   │   ├── task.md
│   │   ├── 灵感闪现.md
│   │   ├── 00-现状数据.json
│   │   └── 10-候选方案.md
│   ├── Z1-验收/
│   │   ├── task.md
│   │   └── 灵感闪现.md
│   ├── 灵感闪现.md
│   └── 复盘.md
├── M2-最终交付/
│   ├── milestone.md
│   └── 灵感闪现.md
└── 项目复盘.md
```

示例文件说明各自位置。用户主动要求留存材料时，Agent 才在对应层级增加编号条目。

## 各层唯一职责

| 原件 | 保存什么 |
| --- | --- |
| project.md | 项目方案：背景、目标/预期、范围、完成条件、总体做法与关键约束；负责人、父子关联；里程碑路线、入口及整体状态。 |
| M目录/milestone.md | 节点目标、达成条件、当前整体判断、计划与任务索引/重点、必要依赖和复盘入口；引用所需任务结果，不另存一套任务状态。 |
| 项目、里程碑、任务根目录的灵感闪现.md | 用户随手记录本层的问题、想法和观察。公共建档创建初始手记，既有手记原文保留。 |
| M目录/字母及任务号目录/task.md | 当前任务要拿到什么、推进到哪里、已取得哪些结果/证据、还缺什么/有何阻塞、下一步及必要触发；关联上下文入口和当前采用结论，保持简短。 |
| 项目根目录/P00、P10 等条目 | 跨里程碑使用的背景、调研和原件。 |
| M目录/M00、M01 等条目 | 本阶段共用的样本、输入和决策依据。 |
| 任务目录/00、10、20 等条目 | 用户要求留存的工作上下文，包括输入、分析、方案、数据包、试验、结果和检查依据。 |
| M目录/复盘.md | 对节点目标验收与过程复盘，写结果/证据、差异、经验、遗留及后续决定；引用任务原件。 |
| 项目根目录/项目复盘.md | 项目整体目标及整合是否达成、总体经验和遗留；引用各节点结论/成果，不复制全套内容。 |

任务主文保留当前工作状态和成果入口，历史过程通过既有对话归档追溯。长分析和实际产物优先引用原件，用户主动要求时再留作编号上下文。任务完成条件写在主文，复杂条件可引用具体原件。

## 当前状态、下一步及关联

以下说明信息归属，字段、状态及程序校验以[治理协议](governance.md)为准：

- project.md持项目状态与当前主要环节，可引用当前重点里程碑；父子项目各持自己的状态。
- milestone.md持节点状态、总体缺口与当前任务重点/协调决定。任务当前状态、结果入口及下一动作由各task.md持有；索引展示时回源，不独立修改第二份。
- task.md的最小元数据可包括稳定id、所属项目/节点引用、status、owner、updated、next_action；正文用短段说明结果和未决，下一步不再抄一份。
- 复盘的status表达本轮复盘完成与否，outcome表达验收结论。复盘已完成不自动等于验收通过；旧评审依据及结果不能被后续改标准覆盖。
- 项目parent_project=null表示顶层，其他项目引用唯一直接父项目；child_projects只列直接子项目。两端使用{id,path}关联并保持一致，禁止自指或祖先循环。
- project.milestones指节点主文；节点project回指项目、tasks指各任务目录内的task.md；任务回指所属节点。id独立于文件名、路径和里程碑/任务编号，不因改名形成新对象。

公共治理接口检查父子关系、路径和状态，专业方法核对实际结果与业务验收。

## 编号上下文怎样推进工作

编号至少两位，按数字排序。名字说明用途或结论。单份材料可直接用文件，多份原件可放在编号文件夹里。应用展开目录时才读取子项。Agent 通过治理 read 发现入口，通过 context-list 查看一层。

一次推进先读取task.md当前状态，再选相关编号原件；解决明确问题，留下新结果并检查；更新当前采用结论、结果入口和下一步。输入/输出/检查关系在task.md或相关原文写明，编号不替代真实依赖。

同一工作跨多轮维护同一个目录和主文。日常推进、测试和验收引用已有原件。用户主动要求把材料留作上下文时，Agent 按材料的用途选择对应层级。

跨层复用时引用材料原件。需要综合判断时，负责该判断的任务产出新的结论，并引用具体源文件。实际代码、已有知识或外部原件保留在原位置。

## 四阶段及收口

| 阶段 | 主要落点 |
| --- | --- |
| 定方案 | 每层project.md中的目标、范围、预期、完成条件与总体做法。 |
| 做计划 | 项目中的节点路线；milestone.md中的任务安排与依赖；明确具体工作后建立字母编号任务目录和简短task.md。 |
| 推进 | task.md 维护当前状态、结果、未决与下一步，按需引用输入和产出原件。影响整体判断时更新节点或项目。 |
| 复盘 | 每个实际节点的复盘.md；有限项目结束/终止时的项目复盘.md。普通任务作相称结果检查，不强制再建任务复盘文件。 |

每个节点都应有阶段性、可验证的结果，完成任务数量不能代替验收。最后交付节点与项目完成条件对齐、必要前序结果具备后，可以同轮完成末节点与项目复盘并收口，不增加归集所有文件的任务或成果包。

简单项目使用一个节点和少量任务；复杂项目增加节点、任务或独立子项目，文件职责保持一致。

## 治理与兼容

治理以项目管理能力原件和程序模型为依据，本文只作解释，能力、模板、CLI和应用使用同一原件。旧 JSON 冻结为历史。采用中转目录的现行项目由用户手动提级，核对索引、依赖、证据和接续入口后再通过治理 check 校验。业务身份沿用原稳定 ID。

## 字母任务阶段的展示说明

本节解释能力包及程序模型，不作为业务定义。里程碑内部用A准备、B—Y用户定义、Z验收复盘等轻量任务阶段；任务目录如B1-具体工作/task.md。阶段定义在milestone.md的task_stages，任务号在task.md的task_code，目录保持平铺。原六状态、依赖和可开始判断分别维护。已有T编号由公共renumber事务预览并迁移，稳定ID、旧正文、历史证据和旧入口接续保留。具体方法与正式模板以项目推进搭档能力包为准，数据约束以runtime项目治理模型为准。
